Dozer Sandbox · the dashboard (doz ui)

Style guide — a living specimen

Every sample on this page is drawn by the dashboard’s real stylesheet, Sources/DozerWeb/WebSource/app.css, loaded in place, with the icons the dashboard vendors and the marks of its icon registry. The markup is what the components in Sources/DozerWeb/WebSource/app/ produce. Light and dark sit side by side — color-scheme is the theme, exactly as in the app.

A change to the dashboard’s look updates this page in the same commit. A sample here that no longer matches the app is a bug in this page.

Rules every piece of the dashboard keeps

  1. Tokens only. Every colour, size, radius, shadow and layer is a var(--…) from app.css :root, with light-dark(); no literal colour anywhere else.
  2. 13 px is the UI size (--fs-md); 14 for prose in wizards and section titles; 16 for a step’s title; 20 for a page or modal title.
  3. One button family — default, .primary, .quiet, .danger, .sm/.lg, .icon-only (with aria-label). One primary per view: the verb that moves forward (Next, Create, Start).
  4. One notice surface: the callout (info · ok · warn · bad). A failure is said where the action started and stays; a toast is only for success.
  5. Never colour alone: a pill is glyph + word; a dimmed option says why in readable text (--ink-2, never --ink-3).
  6. Wizards are the modal (.wiz-modal › .wm-box): wizHead (title, ✕, the step strip), a scrolling .w-body, a footer that never leaves the screen. Quick try is the same modal made full-page (.wiz-modal.full) with a labelled Close.
  7. Choices are cards (.wiz-choice, .base-card, Quick try’s .qt-item): chosen = a ring; a segmented control for 2–4 short modes.
  8. Icons are the vendored Lucide set only (listed at the end). A new icon is a vendoring change (VENDOR.json). Marks (agents, vendors) come from the icon registry, monochrome, in currentColor.
  9. Commands and files are shown exactly, monospace, copyable, never holding a secret; a long file folds away behind a disclosure.
  10. Light and dark both work, and the theme is the app’s switch (data-theme on <html>; auto follows macOS). Text is set with textContent, never markup.

Try’s setup, and every destructive confirmation: a box to tick

Try opens a smaller modal over the Quick try (dialog.dlg.try-setup): every prerequisite — the key (the one it uses, a choice when it can use several, or the card: paste, a source kept outside, what is not offered), the image, the plan — and the final Start; Cancel or Esc leaves nothing behind. A tool with a choice of model gets ONE section, Where TOOL gets its model (components/model-source.js, also New Sandbox's account step): its providers, then the gateways, as equal rows (.ms-src › .ms-opt, a radio each), each with its key status (.pill.st-ok naming the key, or .st-off “no key yet”); the chosen row (.on) holds what it needs under it (.ms-need): the key it uses (a choice when there are several, “Add another key”), or the paste field, where to get a key and the 1Password/AWS/program fold. Then Model: the picker (.ms-picker) — the source's own list (a gateway's public list, read on this Mac once a day), searchable, name · maker · context · price per million tokens, the default tagged; an id that looks like one may be used as typed. What is truly not offered is one quiet line (.ms-notoffer); a tool with one source shows one line (.ms-one). The plan shows the model and “Same in Terminal”. A tool with no choice of model (Claude Code, Codex: their own sign-ins) keeps its Key section. Every destructive confirmation is ONE component (confirmAction / confirmWithCheck in components/dialog.js): a box to tick whose sentence says what happens (“Yes, reset demo”), the button disabled until it is ticked and named by the verb, its icon by the verb (trash for Remove and Delete, rotate-ccw for Reset, history for Revert) — never a name to type. Removing or resetting a sandbox, deleting or reverting to a restore point, removing an account, an image or a template, deleting a try.

The terminal strip

The active tab sits on the terminal’s own dark chrome in both themes; its close, move and session buttons take the terminal’s ink (--term-ink). Tab zero, Console (.tab-console), is the system console: first, its own icon (cpu), no number, no close box, there exactly while the VM is powered on. A tab that is ready but not shown carries a dot (.tab-activity): the agent’s, when ui.boot_view_on_start keeps the page on Console. Left of Console, the build log’s small tab (.tab-buildlog): an icon only (list-checks), its name in the tooltip, read-only, no close box — the image’s last build (its steps with their times, then each step’s whole output), there whenever one is kept, through shutdown and sleep; never chosen by itself.

A start, in the terminal area

After Start the page is there at once and nothing moves. While it starts the area IS the start — no card, at its final width from the first frame: the bar spans the terminal area up to --build-max (1100 px; wider is hard to read). The action bar’s status slot says nothing while the panel shows (a failure and the result still do). The terminal area shows, in the same place: the build, while the image is prepared (.start-progress, components/start-progress.js) — a bar for the whole build that never moves back (steps weighted by this Mac’s last build of the recipe, else by kind; a download fills its share by bytes), “Step N of M · step · elapsed”, the finished steps, and the raw output under “Show details”; then tab zero, Console, when the VM powers on; then the agent’s tab once it has drawn its screen (switched to, or a dot). A cached image shows no bar. A failure keeps the area, with the error, the log, Start again and Dismiss. The header’s pill says Preparing…, then Booting…. When the build ends its log stays, as the small build-log tab left of Console. What the agent was refused is the header’s “N denied” menu, never a banner. A try’s Start moves at once: the button says Starting… with a spinner in the click’s own frame, both modals close, and the try’s page draws its header and an indeterminate “Preparing NAME” panel from the plan while the sandbox is made behind it. A create that fails says so there — “NAME was not made”, the reason, Back to setup (the setup again, with the error) — never only a toast.

    The build log

    The build log’s tab draws a document, not a terminal (components/build-log.js, from the host’s BuildLogDocument — the same record doz image log IMAGE prints): how the image was made. The inputs (the base with its digest, kernel, guest init, the recipe and its version, the bake’s network policy folded, the early steps and which were cached); then each step under a plain heading, with its command or script exactly as it ran in a monospace block (.bl-code), every file it writes (path and contents, folded when long), and its output; then each check — the command, what it expects, what it got. Text only; nothing secret-shaped is ever kept in it.
